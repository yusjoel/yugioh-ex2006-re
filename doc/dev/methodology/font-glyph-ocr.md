# 12×12 像素字库 OCR 流程

通用方法论，适用于「N 个 12×12 像素位图 glyph，需要逆向出 idx → Unicode 字符 1-to-1 码表」类任务。

## 1. 目标

- **输入**：N 个 12×12 像素 glyph（idx 范围 0..N-1）
- **输出**：idx → Unicode 字符的 1-to-1 码表

码表用于解析使用该字库的文本数据（如游戏 ROM 中的卡名/对话/UI 串）。

## 2. 难点

| 类别 | 说明 |
|---|---|
| 分辨率限制 | 12×12 像素下形近字（偏旁差异仅 1-2 像素）极易混淆 |
| 字形变体 | 简体↔繁体↔日文新字体（同字三形）肉眼可分但 OCR 难分 |
| 半角/全角 | ASCII 半角 `a` 与全角 `ａ` 在 OCR 看来几乎一样 |
| OCR 上限 | 12×12 是商用 OCR 的"边界"分辨率，单 pass 准确率 ≤ 90% |

## 3. OCR 引擎选型

实测三款引擎，仅 PaddleOCR 可用：

| 引擎 | 结果 | 备注 |
|---|---|---|
| tesseract | ✗ 弃用 | 12×12 像素下识别率过低，多数 glyph 输出为空或乱码 |
| manga-ocr | ✗ 弃用 | 偏向竖排长文上下文识别，对孤立单字效果差 |
| **PaddleOCR** | ✓ 选用 | 中日字符识别能力相对最强，对汉字 glyph 有可接受的命中率 |

## 4. 核心思路

不依赖任何单次 OCR 输出。整体流程是：

```
字库分区识别 (人工锚点 + 顺序填充)  ← 解决 70% 字符
            +
PaddleOCR (汉字段)  ← 解决剩余 70% 中的大部分
            +
校对源验证 (外部数据库交叉)  ← 修正 OCR 错
            +
视觉确认 (人工最后一道)  ← 修正剩余疑难
```

## 5. 字库分区识别（提速关键）

字库通常按字符类别**连续分布**。先找到分区边界，然后整段顺序填充——无需逐 idx 跑 OCR。

### 5.1 常见连续段

| 段 | 字符 | 数量 | 排序依据 |
|---|---|---|---|
| 数字段 | ０..９ | 10 | Unicode U+FF10..FF19 |
| 大写字母段 | Ａ..Ｚ | 26 | Unicode U+FF21..FF3A |
| 小写字母段 | ａ..ｚ | 26 | Unicode U+FF41..FF5A |
| 平假名段 | ぁ..ん | ~83 | Unicode U+3041..U+3093（含浊音/拗音） |
| 片假名段 | ァ..ヶ | ~85 | Unicode U+30A1..U+30F6 |

### 5.2 锚点法

1. 用 PaddleOCR 跑一遍，找出每段的若干锚点（如 `'A'`、`'あ'`、`'ア'`）
2. 锚点附近的 idx 大概率是同一段
3. 视觉确认 1-2 个锚点 idx 真在该段，则**该段连续多少 idx 的字符可直接按 Unicode 顺序填**
4. 段边界由"字符突然变成另一类"判定（如 `Ｚ`(idx N) → 接下来是汉字 idx N+1）

### 5.3 处理后剩余

去掉以上 5 段（约 230 个 idx）后，剩余基本是**汉字段**——字数最多、最难，是 OCR 的重点。

## 6. 数据源

| 优先级 | 来源 | 作用 |
|---|---|---|
| 高 | 手工 confirmed | 覆盖一切（用户视觉确认结果） |
| 中 | 校对源投票 | 由项目数据反推（见 6.2） |
| 低 | OCR 引擎结果 | 兜底（PaddleOCR 输出） |

### 6.1 OCR 引擎

PaddleOCR 把字库 sheet（多 glyph 拼接图）作为输入，逐 glyph 输出最可能字符。结果存为 `ocr_paddle.json`，作为兜底层。

### 6.2 校对源（核心创新）

利用项目本身已有的「字串 ↔ 已知文本」对应。例如：
- 游戏 ROM 中有卡名/物品名表（自定义编码字节流）
- 外部数据库（如 ygocdb / Wiki）有同字段的 plaintext 文本（jp_name 等）
- 通过卡片 ID（passcode）做 join，得到「字节序列 ↔ Unicode 字符串」配对

**投票方式**：
对每个 idx，统计在所有「字节流位置 → 字符位置」配对中它对应到哪个 Unicode 字符。最高频字符即此 idx 的最可能值。

校对源覆盖率取决于项目数据规模。即便只覆盖 30%-50% idx，也是其余 OCR 结果的强力修正基石。

### 6.3 视觉确认

OCR + 校对源仍有遗漏（生僻字、外部数据库未收录字、字形变体等）。这部分必须人工渲染 glyph 视觉判断（见第 8 节）。

## 7. 优先级合并

逐 idx 取值：

```
codetable[idx] = user_confirmed.get(idx)
              or cardname_vote.get(idx)
              or paddle_ocr.get(idx)
              or empty
```

每次发现新错都加进 `user_confirmed`，下次合并自动覆盖低优先级源。

## 8. 验证方法

### 8.1 字符段约束

各连续段必须严格符合预期编码顺序，违反即错：

| 段 | 约束 |
|---|---|
| 数字 / ASCII 字母 | idx 单调 ↔ Unicode 单调（见 5.1 表） |
| 平假名 / 片假名 | idx 单调 ↔ Unicode 单调（与 JIS X 0208 一致） |
| **汉字段** | **所有字符必须在 JIS X 0208 / SJIS 范围内**，且 idx 单调 ↔ SJIS 字节序单调 |

汉字段尤其重要的额外硬约束：

> **汉字段中的字符必须是 JIS X 0208 (Shift_JIS) 收录的日文汉字**。如果出现简体字、Latin 字母、符号、Unicode 私用区字符，**100% 是 OCR 错**。

实现：
```python
for idx, ch in codetable.items():
    if 该 idx 在汉字段:
        try:
            ch.encode('shift_jis')  # JIS X 0208 编码测试
        except UnicodeEncodeError:
            print(f'idx={idx} {ch!r} 不在 SJIS 范围 → 必错')
```

无 SJIS 映射的字符是 OCR 误识的「头号嫌疑」候选。常见模式：
- 简体 `较` (U+8F83) → 应是日文新字体 `較` (U+8F03, SJIS)
- 简体 `营` (U+8425) → 应是 `営` (U+55B6, SJIS)
- 简体 `值` (U+503C) → 应是 `値` (U+5024, SJIS)

### 8.2 外部数据库交叉

用 cardname-vote 同样的方式，但反过来用：把当前码表解码出的字符串与外部数据库 plaintext 全表 diff，找不一致的位置。**完全匹配率**作为整体质量指标。

### 8.3 码表唯一性

理想码表是 1-to-1（每个字符仅一个 idx）。出现重复说明：
- 多个 idx 被 OCR 错误识别为同一字符
- **或**字库本身有视觉相似的不同字形 glyph（合法重复）

每个重复字符必须人工辨识——典型情况是「字形变体」（如同一字的两种风格）或「OCR 把不同字识为同字」。

## 9. 视觉审阅工具链

OCR 不是 100%，最后总要人工看图。配套工具：

### 9.1 单 idx 高清渲染

把 12×12 glyph 放大 10x-24x 渲染为 PNG，连同当前码表标的字符一起显示。让人能清晰看出每像素结构。

### 9.2 重复字符对比页

把所有「同一字符多 idx」的 glyph 并排渲染，区分谁是「真字」谁是「错标」。频率（在数据中出现的次数）通常是判定依据：高频 = 正确，低频 = OCR 错。

### 9.3 异常 idx 分页审阅

把所有候选异常 idx（违反 SJIS 约束、违反单调性、外部库不匹配等）分页渲染，每页 6-8 个，留 hint 字段。用户可以一次性确认一批。

### 9.4 上下文搜索

某 idx 单纯看 glyph 难辨识时，搜该 idx 在 ROM 中的实际使用上下文。例如某 idx 在 deck 名 `魔王の?宴デッキ` 中，结合 `?宴` 模式可推出 `?` 是 `饗`（饗宴 = 盛宴）。

工具：在所有 JA-encoded 字串中（卡名、卡描述、UI 串）grep 该 idx，把命中的字符串解码成可读形式，肉眼审阅。

## 10. 工作流程总览

```
[初始]
  字库 sheet → PaddleOCR → 粗糙 codetable.json (准确率 ~70%)

[字库分区]
  视觉锚点 → 数字/ASCII/假名段顺序填充 → 覆盖率 ~25-30%

[校对源]
  外部数据库 + 项目内字串↔字符对应 → 投票 → 覆盖率 ~70-90%

[迭代视觉确认]
  for 每轮:
    跑验证 (SJIS 约束、唯一性、外部 diff)
    分页渲染异常 idx
    用户确认 → 加入 user_confirmed
  直到验证全过

[输出]
  1-to-1 codetable.json
```
